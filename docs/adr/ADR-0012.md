# ADR-0012: Spring Boot platform API in front of the agent service

**Status:** Accepted
**Date:** 2026-11-24
**Refines:** ADR-0005 (service boundaries), ADR-0009 (contract-first platform API)

## Context

ADR-0009 shipped a Python reference facade of `contracts/openapi/platform-api.yaml` because the
Spring Boot backend could not be built (registries unreachable). The registries are reachable
now, and the platform is meant to be the control plane: authentication, who may approve, the
record of approvals, and audit.

## Decision

1. `apps/backend` (Spring Boot 3.5, Java 21) implements the platform API. It authenticates callers
   (HS256 platform tokens locally, with a dev sign-in only in the `local` profile; OIDC through
   `copilot.auth.oidc-issuer-uri`, with the same claim checks), derives tenant and roles from the
   verified token only, and relays run, catalog and conversation calls to the agent service with a
   short-lived (120 s) service token naming the acting user. Responses pass through unchanged; errors
   are re-shaped to `ApiError`.
2. **Approvals belong to the platform.** Spring checks the approver role, requires the displayed
   action hash to match the pending action (409 otherwise), mints the action-bound approval token
   (the format of `skills/runtime/approvals.py`, pinned by a known-answer test) and resumes the run.
   The agent's runtime still verifies and consumes each token exactly once.
3. The agent service owns run state and conversations (ADR-0010) and gains the internal endpoints the
   platform needs: catalog reads, run listing, conversations, reject, and `approver` on resume.
4. Spring's own durable state is PostgreSQL via Flyway: approval decisions (one per run and action
   hash) and an audit log. Run state is deliberately not duplicated.
5. The contract suite (`tests/contract`) runs unchanged against both implementations: the in-process
   Python facade and the Spring jar (with PostgreSQL behind it and the Python agent service in
   front of the sandbox).
6. Dropped from the scaffold: JPA, Redis, WebFlux, Spring AI, springdoc and the unused schema
   (never deployed). Model calls stay in the agent service.

## Alternatives considered

| Option | Trade-off |
|---|---|
| Keep only the Python facade | Nothing owns identity and approvals outside the AI process; ADR-0005's boundary stays fiction |
| Spring owns runs and conversations too | Duplicates run state and needs history built in Java; the agent already persists and tenant-scopes it |
| Spring Boot 4.x now | The supported line, but this change needed the long-known 3.5 APIs; the upgrade is a follow-up |

## Consequences

- Two implementations of one contract must be kept in step; the shared suite fails if they drift.
- The approval key and the service-token key are shared secrets between Spring and the agent
  (asymmetric keys or KMS are the production follow-up).
- Spring Boot 3.5's OSS support has ended; moving to 4.x is tracked in STATUS.md.
- The OIDC path is configured but has not been exercised against a real identity provider.
