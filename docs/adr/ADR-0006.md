# ADR-0006: Skill Contract, Policy Enforcement and Action-Bound Approvals

**Status:** Accepted
**Date:** 2026-10-03

## Context

The original executor skill fetched any URL with any headers. Nothing tied a human
approval to what was actually executed, and nothing prevented a replayed or duplicated
side effect. MCP was used as the only contract, but MCP tool schemas say nothing about
permissions, side effects or idempotency.

## Decision

Every skill is a `SkillDefinition` with: id, name, semantic version, description,
Pydantic input and output models (JSON Schema derived from them), required permissions,
side-effect class (`NONE`, `READ`, `WRITE`, `DESTRUCTIVE`), timeout, retry policy,
idempotency requirement, audit requirement, error contract (enumerated `SkillErrorCode`),
and an execution function.

All invocations go through `SkillRuntime.invoke(...)`, which in order:

1. resolves the skill (unknown → `UNKNOWN_SKILL`);
2. validates input against the input model (→ `INVALID_INPUT`);
3. checks the target environment against an explicit allowlist (→ `ENVIRONMENT_NOT_ALLOWED`);
4. asks the PDP whether the principal holds every required permission in that tenant and
   environment (→ `FORBIDDEN`);
5. for `WRITE`/`DESTRUCTIVE` skills, requires an **approval token** whose action hash equals
   `sha256(canonical_json({skill_id, skill_version, arguments, environment, tenant, subject}))`,
   that is unexpired, HMAC-valid, and **unused** (→ `APPROVAL_REQUIRED` / `APPROVAL_INVALID`);
6. enforces idempotency keys for side-effecting skills: same key + same action → cached
   result; same key + different action → `IDEMPOTENCY_CONFLICT`;
7. executes with a timeout and bounded retries for retryable error classes only;
8. validates output against the output model;
9. emits an audit event (redacted arguments, outcome, durations) and telemetry.

MCP is an **adapter**: the MCP server lists tools from the registry and forwards calls to
the runtime with the caller's principal. There is no code path from MCP to a skill
function that skips the runtime.

## Alternatives considered

| Option | Trade-off |
|---|---|
| Approval as a boolean flag on the run | Cannot detect argument/environment changes after approval. |
| Approval stored only server-side, matched by run id | Still needs exact-action binding; we use both: token for integrity, store for single use. |
| JWT for approval tokens | Works, but HMAC over a canonical payload is simpler and has no algorithm-confusion surface. |
| Rely on MCP tool annotations (`destructiveHint`) | Hints are advisory and client-interpreted; not an enforcement mechanism. |

## Consequences

- The model can propose any call, but cannot execute a write without a human approving
  the exact hash; changing a single argument or the environment invalidates the approval.
- The approval signing key is a secret of the AI service (dev default refuses to start
  outside `local`/`test`).
- Durable single-use tracking needs the platform's approval store; the in-memory store is
  for tests and single-process local runs only.
