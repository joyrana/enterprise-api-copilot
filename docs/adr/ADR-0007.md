# ADR-0007: PostgreSQL + pgvector as the Single Data Foundation

**Status:** Accepted
**Date:** 2026-10-03

## Context

Docs and config listed PostgreSQL, Redis and "pgvector / Qdrant". Redis was wired into
the backend with no usage; Qdrant had configuration but no code.

## Decision

- PostgreSQL (17 in Compose) with pgvector is the only required datastore.
- Schemas per owner: `platform` (Flyway, Java) and `knowledge` (AI service SQL migrations
  in `ai/knowledge/sql/`). No cross-schema reads between services.
- Retrieval uses both pgvector (dense, HNSW) and PostgreSQL full-text search (`tsvector`),
  fused with Reciprocal Rank Fusion (RRF, k = 60) — the same fusion the in-process
  retriever uses, so offline evaluation and the database path are comparable.
- Redis and Qdrant are removed from the default stack. Redis may return behind a profile
  when a measured need appears (e.g., distributed rate-limit counters).
- Index parameters (HNSW `m`, `ef_construction`, chunk size/overlap) are chosen from
  retrieval benchmarks, not defaults copied from blog posts. Until benchmarks exist, pgvector
  defaults are used and labelled as such.

## Alternatives considered

| Option | Trade-off |
|---|---|
| Qdrant as primary vector store | Strong ANN performance, but a second stateful service and no transactional consistency with document metadata and ACLs. |
| Elasticsearch/OpenSearch for hybrid | Good BM25; another cluster to operate; ACL filtering duplicated. |
| Separate graph DB for API relationships | No relationship query yet needs graph traversal beyond a few joins. |

## Consequences

- Tenant filtering is a `WHERE tenant_id = $1` on the same rows as embeddings — no
  cross-store ACL drift.
- If corpus size or latency targets outgrow pgvector, the `Retriever` interface allows a
  second implementation; benchmarks must justify it.
