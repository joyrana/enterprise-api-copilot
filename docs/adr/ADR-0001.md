# ADR-0001: Core Technology Stack Selection

**Status**: Accepted  
**Date**: August 2026  
**Deciders**: Architecture Team  
**Tags**: infrastructure, ai, cli, gateway

---

## Context

Enterprise API Copilot is a new platform that must support agentic AI workflows, enterprise API management, a developer CLI, and a web frontend. We need to choose the core technology stack for each layer with consideration for long-term maintainability, ecosystem maturity, and fit-for-purpose.

---

## Decision 1: LangGraph for AI Orchestration

### Decision

Use **LangGraph** (Python) as the AI agent orchestration framework.

### Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| LangGraph | Stateful graphs, streaming, human-in-loop, TypeScript support | Python primary, learning curve |
| CrewAI | Simple multi-agent setup | Less control over state, limited streaming |
| AutoGen | Good for code generation | Less production-ready orchestration |
| Custom LLM Chains | Full control | High development overhead, no graph structure |

### Rationale

- LangGraph provides a **stateful, cyclical graph** execution model, which maps directly to our Supervisor → Planner → Executor → Reflection agent pipeline.
- Built-in **human-in-the-loop** support is critical for enterprise use cases where approval gates are required.
- Native **streaming** support allows real-time output to CLI and frontend.
- **LangSmith** integration gives us immediate observability into agent execution.
- Strong community momentum and backing from LangChain Inc.

### Consequences

- Agent service will be Python 3.12+.
- Backend communicates with agent service via HTTP/SSE.
- Agents are deployed as a separate service (not embedded in the JVM).

## Decision 2: Spring Boot 3 for Backend API

### Decision

Use **Spring Boot 3** (Java 21) as the backend framework.

### Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Spring Boot 3 + Java 21 | Enterprise maturity, Spring AI, virtual threads, vast ecosystem | Verbose, higher memory footprint |
| Quarkus | Faster startup, lower memory | Less ecosystem, smaller community |
| Node.js + Fastify | Fast I/O, TypeScript | Less mature enterprise patterns |
| Go + Gin | Fast, simple | Limited ORM, enterprise integrations require more code |

### Rationale

- **Spring AI** provides first-class integration with OpenAI, embedding models, and vector stores — reducing boilerplate.
- **Java 21 virtual threads** (Project Loom) address the traditional Spring blocking I/O concern.
- Spring's **mature ecosystem** (Spring Security, Spring Data, Spring Actuator, Micrometer) covers all enterprise requirements out-of-the-box.
- **Spring Boot Actuator** gives us production-ready health, metrics, and tracing endpoints immediately.
- The engineering organization has existing Java 21 expertise.

### Consequences

- Maven used as build tool for consistency across Java ecosystem.
- Backend package structure follows Domain-Driven Design with hexagonal architecture.
- PostgreSQL via Spring Data JPA + Flyway for migrations.

## Decision 3: Go + Cobra for CLI

### Decision

Use **Go** with **Cobra** and **BubbleTea** for the developer CLI.

### Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Go + Cobra | Single binary, fast startup, rich TUI (BubbleTea) | Requires Go knowledge |
| Python + Click | Easy development | Requires Python runtime, slow startup |
| Node.js + Commander | TypeScript support | Requires Node.js runtime |
| Java CLI (picocli) | Same language as backend | JVM startup time, heavy distribution |

### Rationale

- Go produces a **single statically-linked binary** — critical for easy installation (`brew install`, direct download).
- **Zero runtime dependencies** means the CLI works anywhere without requiring Python, Java, or Node.js.
- **Cobra** is the de facto standard for Go CLIs (used by kubectl, docker, gh).
- **BubbleTea** enables rich terminal UI with spinners, tables, and interactive prompts.
- Go's **fast startup time** (~5ms) is essential for a developer tool.

### Consequences

- CLI communicates only with the Backend REST API.
- CLI stores credentials in the OS keychain / `~/.config/copilot/`.
- Distribution via GitHub Releases as pre-built binaries and Homebrew tap.

## Decision 4: MCP (Model Context Protocol) for Skills

### Decision

Use **MCP (Model Context Protocol)** as the standard interface for AI skills.

### Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| MCP | Standardized, composable, multi-runtime | Relatively new (Anthropic, 2024) |
| LangChain Tools | Familiar to LangGraph | Tied to Python/LangChain |
| OpenAI Function Calling | Native OpenAI support | Vendor-locked, no multi-model |
| Custom Tool Interface | Full control | No standardization, harder to share |

### Rationale

- MCP is an **open standard** (not vendor-locked) that is rapidly being adopted across the AI ecosystem.
- Skills can be implemented in **any language** and exposed over stdio/HTTP — allowing Java skills, Go skills, or Python skills.
- MCP's typed tool interface provides **schema validation** and **self-documentation** for free.
- The protocol is **composable** — skills can be combined, reused, and shared across different agent systems.

### Consequences

- Each skill is an independent MCP server with its own process boundary.
- Skills are invoked by agents via the MCP protocol, not direct function calls.
- Skills can be tested in isolation without running agents.

## Decision 5: Apigee for API Gateway

### Decision

Use **Apigee X** as the enterprise API gateway for authentication and API management.

### Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Apigee X | Enterprise features, GCP native, analytics, developer portal | GCP dependency, cost |
| Kong | Open source, Kubernetes native | Less enterprise analytics |
| AWS API Gateway | AWS native | Vendor-locked to AWS |
| Nginx + custom auth | Full control | High maintenance overhead |

### Rationale

- **Apigee** is the enterprise standard for API management in large organizations.
- Built-in **OAuth 2.0, API key management, quota enforcement, and threat protection**.
- **Apigee developer portal** gives API consumers a self-service experience.
- **Analytics dashboard** provides usage metrics and API health at the gateway layer.
- The target enterprise customers typically already have Apigee deployed.

### Consequences

- All external API calls are proxied through Apigee.
- JWT tokens are issued and validated by Apigee.
- Apigee proxy configurations are version-controlled in `apigee/`.
- The platform supports non-Apigee deployments through an `ApiGatewayPort` abstraction.
