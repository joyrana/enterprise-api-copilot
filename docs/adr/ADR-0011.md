# ADR-0011: LLM-driven agent with code-enforced guardrails

**Status:** Accepted
**Date:** 2026-11-24
**Refines:** ADR-0006 (skill contract, policy, action-bound approvals), ADR-0008 (offline evaluation)

## Context

The agent began as rules → template plan → template reply. A model now classifies intent,
plans each step in a bounded ReAct loop and writes the reply and chooses UI components
(`ai/agent/`). The default model is Qwen3-4B on a local `mlx_lm.server`, which ignores
`response_format`, so output is not schema-constrained. A small model will sometimes be
wrong, malformed or manipulated by text it reads, so safety cannot depend on it behaving.

## Decision

**The model proposes; code decides.** Every model output is a proposal that deterministic
code validates before it has an effect. With a model configured there is no rules/template
fallback; model failures end the run explicitly (with the G9 exception below).

### Invariants (each has tests)

1. Principal, tenant, environment, approvals and permissions never come from model output
   or request text.
2. The planner can only call skills the intent resolver allowed. Every `api.call.*` needs a
   prior successful `api.describe` of the same operation and its `invocation_skill`.
3. Argument values must be grounded in the user's request (or, once G3 lands, in successful
   `api.call.*` output of the same run and tenant, with provenance). Documentation text is
   never a grounding source.
4. Every WRITE/DESTRUCTIVE call pauses for approval bound to the exact action hash; the
   approval UI is server-controlled.
5. Untrusted content (docs, API responses) reaches the model only as delimited untrusted
   context, never in the system prompt.
6. No secret reaches a model provider or logs unredacted. `generate_structured` applies
   `sanitize_request` to every attempt (JWTs → `<JWT>`, other credentials → `[REDACTED]`).
7. With a model configured there is no rules fallback. Model failures end the run
   explicitly. **Exception (G9):** if a side-effecting step already succeeded and a later
   model call fails, the run ends `COMPLETED` with a message that the action succeeded and
   the summary could not be generated, plus a `summary_unavailable` event. Reporting
   `FAILED` there would invite a retry of an action that already happened.
8. Every HTTP response conforms to `contracts/openapi/*.yaml`.
9. Another tenant's run or data is indistinguishable from a missing one.
10. Unit and contract tests are offline and deterministic (scripted models).

## Alternatives considered

| Option | Trade-off |
|---|---|
| Rules-first, model only as fallback | Predictable, but brittle on phrasing and hides model quality problems behind templates. |
| Model tool-calling without an intent resolver | Fewer moving parts, but the model could reach any skill; the resolver bounds blast radius for a 4B model. |
| Fall back to templates when the model fails | Silent quality cliff; masks outages. Rejected (invariant 7). |

## Consequences

- Model quality affects usefulness (latency 13–25 s, retries), never authorisation.
- Secret masking is lossy: a request that legitimately names a credential-shaped string
  (e.g. `password=…`) is masked before the model sees it.
- Runs can be `COMPLETED` with a degraded message; clients should surface
  `summary_unavailable` events.

## Open risks

- Pattern-based redaction misses novel credential shapes; key-based redaction only covers
  structured data.
- A 4B model can mis-rank skills or loop; mitigated by budgets, rejection limits and skill
  withdrawal, and measured by the `agent_llm` suite (`docs/evaluation/README.md`). On the
  multi-hop case "refund the latest captured payment" the model does not reliably finish the
  chain, so grounding from earlier API results is proven by tests, not yet by a live run.
- Grounding checks values, not meaning: a grounded but wrong id is still caught only by the
  approval summary a human reads.
